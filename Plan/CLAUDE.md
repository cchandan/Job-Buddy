# Job Buddy Claude Instructions

Read these before making changes:

* `spec.md`
* `DESIGN.md`
* `IMPLEMENTATION_PLAN.md`

Project rules:

* This is a real product in daily use by a family, holding their CVs and job applications. Do not treat it as a demo: never lose or expose data.
* Keep the solution simple. Four people use it; do not build for scale that does not exist.
* Do not add unnecessary frameworks, services, infrastructure or dependencies.
* Backend/app language: Python.
* Web app: FastAPI + Jinja templates, server-rendered. No separate JavaScript frontend.
* Database: SQLAlchemy reading `DATABASE_URL`. Postgres (Supabase) in production, always. SQLite only for tests and quick local work.
* Every change to the database's shape is an Alembic migration. Never drop or recreate tables that hold real data.
* Hosting: Render for the app, deployed from GitHub.
* Sign-in is username and password. Accounts are created only by an admin; there is no sign-up, no third-party login and no anonymous use. The role (`user`, `admin`) is set on the account.
* Passwords are generated by the app, shown once, and stored only as salted hashes. Never log, email or display a password after it is created.
* Home (users) and Admin home (admins) are the landing pages. They hold no data of their own; everything on them is derived from the Tracker, CVs and jobs.
* Every route uses the guards in `app/auth.py`. A user may only ever reach their own Home, Tracker, Calendar, Profile and CVs; only admins reach Admin routes or another user's data. Never read a person id from a form or URL without passing it through `target_user`.
* Any new route gets an access test before it is considered done.
* AI access must go through `app/ai.py`, including the daily limit and output validation. The provider (Gemma 4 via the Gemini API today) may change; nothing outside `app/ai.py` may depend on which one it is.
* Never trust AI output: every skill name goes through `app/skills.py`, every evidence quote must appear word-for-word in the source text, and every deadline must parse as a real date.
* AI reads and writes text; deterministic code decides. Listing status, application status, deadlines, de-duplication, access and sync are plain code. Do not move them into prompts.
* A tailored CV may only reorder, select and reword what is in the core CV. It must never invent an employer, title, qualification, date or skill.
* Job fetching uses JobSpy and runs only on an admin's laptop, never on the server. JobSpy goes in `requirements-ingest.txt`, not `requirements.txt`.
* Sync writes only the shared jobs table and the sync history. It must never change a Tracker entry, an application status, a hand-set deadline or a CV, and never delete a job.
* Deadline and status appear wherever a job appears, using the shared chips and badges in `DESIGN.md`.
* CVs live only in the database. Never log CV text. Never commit CVs or secrets; all keys come from environment variables (`.env` locally, host settings in production).
* Everything that changes data is a form POST with a CSRF token, never a link.
* Show friendly error, empty and loading states; never a raw error page. The app must stay usable when AI is unavailable.
* Implement one slice at a time from `IMPLEMENTATION_PLAN.md`.
* Do not add features outside `spec.md` unless explicitly asked. Project Ideas, Network, Skill Gaps, This Week, dream jobs and match ranking are removed; do not bring them back.
* Keep changes small and easy for a non-technical user to understand.
* Before finishing a slice, run the tests and check the acceptance criteria.
